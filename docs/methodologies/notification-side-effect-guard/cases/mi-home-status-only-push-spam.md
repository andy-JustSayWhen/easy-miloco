# 案例：米家误报修复类推送刷屏

返回主文档：[通知类副作用保护方法论](../index.md)

## 现象

用户手机连续收到同类米家推送，文案大意为：

```text
刚才客厅的水浸卫士误报了一次，应该是客厅地面的瓷砖反光导致的，不用担心。
```

这类文案的问题不只是“重复”，而是“本身不该推送”。它已经明确说了误报、原因和不用担心，属于状态说明，不是告警。

## 根因判断

| 观察 | 判断 |
| --- | --- |
| 多次出现同一文案 | 存在重复调用或重试 |
| 文案包含“误报”“不用担心” | 属于 status-only 消息 |
| 用户不需要处理 | 不应走手机推送 |
| 如果只做去重 | 第一条仍会打扰用户 |

结论：应先静默 status-only，再做短窗口去重。

## 修复方式

后端在 `POST /api/miot/send_notify` 出口前增加判断：

| 条件 | 动作 |
| --- | --- |
| 误报类 + 无需处理 | 静默，不调用米家推送 |
| 恢复类 + 无需处理 | 静默，不调用米家推送 |
| 同一文案短时间重复 | 静默，不调用米家推送 |
| 真正需要处理的告警 | 放行 |

API 返回保持成功语义：

```json
{
  "code": 0,
  "message": "Status-only notification suppressed",
  "data": {
    "suppressed": true,
    "reason": "status_only"
  }
}
```

## 验证方式

用同类 status-only 文案请求米家推送接口，预期：

- HTTP 返回 `code=0`
- `data.suppressed=true`
- `data.reason=status_only`
- 后端日志出现 `Suppressed status-only Mi Home notification`
- 手机不再收到这类推送

## 可复用经验

| 经验 | 说明 |
| --- | --- |
| 不要把“修复完成”推给用户 | 自动修复成功后默认静默 |
| 只推需要用户处理的事 | 告警、确认、授权、失败才打扰 |
| 静默也要写日志 | 方便排查为什么没有发通知 |
| 返回成功而不是失败 | 避免上游 Agent 误以为失败并重试 |
